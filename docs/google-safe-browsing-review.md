# Google 安全浏览整改与审核说明

本次针对 Search Console 的“欺骗性网页”报告加固公开入口、登录跳转和 Grafana 嵌入链路。报告提供的是受影响网址示例，不是 Google 的具体命中规则；代码加固不等于已经证明误报或排除了服务器入侵。

## 代码整改

- `/` 进入公开产品介绍 `/product`；工作台仍通过 `/dashboard` 等原入口访问并执行认证和权限校验。
- 新增无需登录的 `/about`，说明项目身份、账号用途、本机存储、外部集成和联系方式；产品页、登录页均有入口。
- 登录页明确只使用本站平台账号，提醒不要填写第三方账号密码。登录返回地址统一校验，拒绝站外、协议相对地址、反斜杠和编码后的异常路径。
- Axios 校验包含 `baseURL` 在内的最终请求地址，拒绝将平台 API 请求和认证信息发送到其他源。
- Grafana 配置在后端校验 `url`、`default_path` 及每个看板的 `full_url`、`url`、`path`。拒绝可执行协议、内嵌账号密码、控制字符、反斜杠和协议相对地址；部分更新也检查保留值。
- 观测概览过滤历史配置中的危险看板链接；前端对实际打开、嵌入的地址再次校验，解析失败时不再使用原始字符串。
- Grafana iframe 标明服务地址，使用 `no-referrer` 并增加 sandbox，未授权表单提交、弹窗、下载和顶层导航。保留 `allow-scripts allow-same-origin` 以兼容看板请求；同源脚本仍具有较强能力，sandbox 不能代替对 Grafana 服务的信任与安全维护。
- 移除外部字体 CSS 请求，主题初始化改用本站脚本。Django 提供的 SPA 页面增加 `script-src 'self'`、`form-action 'self'`、`object-src 'none'`、`base-uri 'self'`、`frame-ancestors 'self'`，以及 Referrer-Policy 和 Permissions-Policy。

HTTP 地址仍支持内网 Grafana 和 HTTPS 站内代理；HTTPS 页面不能直接打开未被代理的 HTTP 看板。合法的 HTTP/HTTPS 地址不代表服务内容一定可信，本次未实现 Grafana 域名白名单或服务端请求的 SSRF 全面防护。

## 上线后再提交

代码与线上生效检查已完成。提交前仍需确认下列清单中涉及站点所有权、异常变更和 Google 抓取结果的事项；不要把未执行的入侵清理或凭据轮换写入审核说明。

1. 按既有部署流程发布前后端，清理入口代理或 CDN 中的旧 HTML 缓存，确认 www 与非 www 域名均使用新版本。
2. 检查报告列出的首页、登录页和带完整查询参数的 Grafana 页面，以及 `/product`、`/about`。未登录访问管理页面仍应进入本站登录流程；合法账号登录后的权限行为应保持正常。
3. 核对线上 Grafana 的数据库配置和 `/grafana/` 代理的真实上游，删除陌生看板与接入地址。若看板需要登录，请使用“全屏打开”在独立页面登录；iframe 内的表单提交受到 sandbox 限制。
4. 用浏览器网络面板及响应头检查确认 CSP 生效。若 Nginx 直接提供静态 HTML，Django 中的响应头不会生效，需在 SPA HTML 的实际响应位置配置等价策略；不要把此策略直接套用到 Grafana 上游，否则可能阻止其必要脚本。部署了自定义 RUM、统计或其他外部脚本的环境，应先逐项确认来源再制定策略。
5. 检查 DNS、Search Console 所有者、服务器访问和操作日志、Web 根目录及反向代理配置，确认没有陌生变更。发现入侵后另行清理漏洞、持久化入口及受影响凭据，不能只靠页面文案整改。
6. 在 Search Console 使用网址检查核对抓取结果，完成以上验证后，从“安全问题”提交一次审核请求。不要在待审核期间重复提交。
